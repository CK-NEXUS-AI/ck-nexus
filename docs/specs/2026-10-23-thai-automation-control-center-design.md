# แบบออกแบบ: ศูนย์ควบคุม Automation ภาษาไทย

วันที่: 2026-10-23
สถานะ: รอผู้ใช้ตรวจเอกสารก่อนจัดทำแผนลงมือพัฒนา

## 1. เป้าหมาย

พัฒนาหน้าศูนย์ควบคุมภาษาไทยที่ใช้งานจริง เชื่อมกับ n8n API ที่มีอยู่ ให้ผู้ใช้สามารถตรวจดู Workflow, สร้าง Workflow จากคำสั่งภาษาไทย, แก้ไขแผนผังแบบภาพ, บันทึก, ทดลองรัน, เปิด/หยุด และตรวจประวัติผลการทำงานได้ โดยคงระบบ n8n เป็น execution engine เดิม

## 2. สภาพปัจจุบันที่ตรวจพบ

- UI: `/root/ck-nexus/creator_app/web/n8n-workflows.html`
- Backend: `/usr/local/libexec/cknexus_n8n_workflows_ui.py`
- systemd service: `cknexus-n8n-workflows-ui.service`
- Bind address: `127.0.0.1:8791` (ไม่เปิด public โดยตรง)
- API key file: `/root/.config/n8n/api_key`; ต้องไม่อ่านค่าออก log, browser, response หรือเอกสาร
- Health endpoint ตอบ `HTTP 200`
- Workflow list endpoint ตอบ `HTTP 200` แต่จำนวน Workflow ที่ API ส่งกลับขณะตรวจคือ 0
- หน้าเว็บเดิมแสดงรายการ/สถานะและรีเฟรชเท่านั้น
- Git มีการแก้ไขและไฟล์ใหม่ที่ยังไม่ commit อยู่หลายรายการ ต้องรักษาทั้งหมด ห้าม checkout/reset/เขียนทับโดยไม่เกี่ยวข้อง
- ยังไม่เชื่อมหน้าใหม่นี้เข้ากับระบบส่วนอื่นของ CK-NEXUS โดยอัตโนมัติ

## 3. ทางเลือกและข้อสรุป

### ทางเลือก A — หน้าควบคุมแบบปุ่มพื้นฐาน
ทำรายการ Workflow, สร้าง/เปิด/หยุด และประวัติ โดยไม่มี editor แบบลากวาง
ข้อดี: ใช้เวลาน้อย ความซับซ้อนต่ำ
ข้อจำกัด: ไม่ตอบโจทย์ Visual Workflow Editor

### ทางเลือก B — ศูนย์ควบคุม + ตัวสร้างภาษาไทย + Visual Editor (เลือกใช้)
คง backend gateway ขนาดเล็กบน VPS, เพิ่ม API ฝั่งเซิร์ฟเวอร์ที่จำเป็น และ UI ภาษาไทยแยกเป็นส่วน: ภาพรวม, สร้างงานภาษาไทย, editor, รายการงาน, ประวัติ และการเชื่อมต่อ
ข้อดี: ตรงความต้องการ ใช้ n8n เป็นระบบรันงานเดิม แยกขอบเขตชัด
ข้อจำกัด: ต้องตรวจสอบ schema/ความสามารถ API ของ n8n รุ่นที่ให้บริการจริงก่อนเปิดใช้การแก้ไขและสั่งรัน

### ทางเลือก C — สร้างแพลตฟอร์ม automation ใหม่ทั้งหมด
สร้าง engine, scheduler, credential vault และ editor ใหม่
ข้อดี: ควบคุมได้เต็มที่
ข้อจำกัด: ซ้ำซ้อน เสี่ยงสูง และไม่เหมาะกับเป้าหมายปัจจุบัน

## 4. สถาปัตยกรรมที่เสนอ

1. **UI ภาษาไทย**: HTML/CSS/JavaScript แบบตอบสนองมือถือและเดสก์ท็อป ใช้ข้อความภาษาไทยทั้งหมด ยกเว้นชื่อเทคนิคที่จำเป็นพร้อมคำอธิบาย
2. **Backend gateway**: Python service ปัจจุบันเป็นจุดกลางเรียก n8n API ด้วย key ฝั่งเซิร์ฟเวอร์เท่านั้น
3. **n8n**: เป็นแหล่งข้อมูลจริงและตัวประมวลผล Workflow; ไม่สร้างฐานข้อมูล Workflow ซ้ำโดยไม่จำเป็น
4. **ตัวแปลงคำสั่งภาษาไทย**: แปลงข้อความเป็นแผนขั้นตอนที่มีโครงสร้าง ตรวจความครบถ้วนและความสามารถของ node ก่อนสร้าง Workflow; ถ้าไม่มี LLM/บริการแปลภาษาที่พร้อมใช้งาน ให้แสดงตัวสร้างแบบฟอร์ม/แม่แบบแทน ห้ามแสร้งว่ามี AI สร้างสำเร็จ
5. **Visual Editor**: แสดง node และเส้นเชื่อมจาก Workflow JSON ของ n8n; การบันทึกต้อง serialize กลับเป็น schema ที่ API รุ่นจริงรองรับ
6. **การเชื่อมต่อบริการ**: แสดงสถานะการเชื่อมต่อและแนวทางตั้งค่า OAuth/credentials; ห้ามอ่านหรือส่ง secret/token ไปยัง browser

## 5. หน้าจอและพฤติกรรม

### 5.1 หน้าหลัก
- แสดงจำนวน Workflow, สถานะ active/inactive และข้อผิดพลาดจาก API จริง
- ปุ่มรีเฟรชและทางลัดสร้างงาน
- แสดงเวลาอัปเดตและข้อความผิดพลาดที่เข้าใจง่าย

### 5.2 สร้างงานด้วยภาษาไทย
- ช่องคำสั่งภาษาไทยและแม่แบบเริ่มต้น
- สรุป trigger, ขั้นตอน, บริการ/credentials ที่ต้องใช้ และผลกระทบก่อนสร้าง
- ตรวจ node/parameter ที่ยังขาดและแจ้งผู้ใช้ก่อนบันทึก
- แยกการสร้างฉบับร่างออกจากการเปิดใช้งานจริง

### 5.3 Visual Workflow Editor
- วาด node และเส้นเชื่อมตาม workflow จริง
- เพิ่ม/ลบ node จากชุดที่รองรับ, เชื่อม/ยกเลิกเส้น, แก้ชื่อและพารามิเตอร์
- ตรวจโครงสร้างก่อนบันทึกและแสดงข้อผิดพลาดเป็นภาษาไทย
- มีสถานะ unsaved changes และยืนยันก่อนทิ้งการแก้ไข
- ห้ามบันทึก node/parameter ที่ไม่รองรับเงียบ ๆ

### 5.4 รายการและการควบคุม
- ค้นหา Workflow และดูสถานะ
- เปิด/หยุดใช้งานและทดลองรันผ่าน server-side API
- ยืนยันก่อนการกระทำที่อาจส่งข้อมูลภายนอกหรือเรียกบริการจริง
- ป้องกันการส่งคำสั่งซ้ำจากการกดปุ่มหลายครั้ง และแสดงผลตอบกลับจาก API จริง

### 5.5 ประวัติ
- อ่าน execution history จาก n8n API หาก API key และรุ่นที่ใช้งานรองรับ
- แสดงสถานะ, เวลา, workflow, ข้อผิดพลาด และลิงก์/รายละเอียดเท่าที่ API ส่งคืน
- ถ้า endpoint ไม่มีสิทธิ์หรือไม่รองรับ ให้แจ้งชัดเจน ไม่สร้างข้อมูลจำลอง

### 5.6 เชื่อมต่อบริการ
- แสดงบริการที่พร้อม/ยังไม่ได้ตั้งค่า
- OAuth ต้องใช้ redirect URI ที่กำหนดไว้, state/PKCE ตาม flow ที่เหมาะสม, least privilege และ token storage ฝั่งเซิร์ฟเวอร์
- ไม่เก็บ client secret หรือ refresh token ใน frontend หรือ source control
- การอนุญาตบัญชีภายนอกต้องผ่านหน้าความยินยอมของผู้ให้บริการ

## 6. ขอบเขต API ฝั่ง gateway

ออกแบบ endpoint ภายในสำหรับ:
- health/status
- รายการและรายละเอียด Workflow
- สร้าง/อัปเดต Workflow
- เปิด/หยุด Workflow
- ทดลองรัน Workflow
- รายการ execution และรายละเอียด execution
- ตรวจสอบความสามารถ/ชนิด node ที่รองรับ

ก่อน implementation ต้องตรวจ API documentation/response จริงของ n8n instance และสิทธิ์ API key โดยเฉพาะรูปแบบ JSON ของการสร้าง/อัปเดต, activate/deactivate, execution และ pagination ห้ามสมมติว่า endpoint ทุกตัวรองรับ

## 7. ความปลอดภัยและการปฏิบัติการ

- คง bind เฉพาะ loopback `127.0.0.1:8791` จนกว่าจะออกแบบ authentication/proxy อย่างชัดเจน
- API key อ่านเฉพาะฝั่ง backend; ห้ามบันทึก secret ลง log, HTML, JavaScript หรือข้อความ error
- validate method, path, JSON size, required fields และ workflow ID; ปฏิเสธ input ที่ไม่ถูกต้องแบบ fail-closed
- ป้องกัน CSRF/คำขอข้ามต้นทางตามวิธี deploy จริง และไม่เปิด CORS กว้าง
- escape ข้อมูลจาก API ก่อน render; หลีกเลี่ยงการแทรก dữ liệu ไม่เชื่อถือเป็น HTML
- เพิ่ม timeout, ข้อความ error ที่ไม่เผยข้อมูลลับ และการป้องกันคำสั่งซ้ำ
- ไม่แก้ระบบ OAuth/credential จนกว่าจะมี client configuration และ redirect URI ที่ผู้ดูแลตั้งค่า
- ไม่เปลี่ยนบริการหรือผูกเข้ากับ CK-NEXUS ส่วนอื่นโดยไม่ได้รับอนุมัติแยก

## 8. การทดสอบและเกณฑ์ยอมรับ

1. Health/UI/API ใช้งานได้หลัง deploy และ service ยัง active
2. API key ไม่ปรากฏใน browser, response, log หรือไฟล์ static
3. รายการและรายละเอียดตรงกับ n8n จริง รวมกรณี 0 รายการ, pagination, timeout และ HTTP error
4. สร้าง Workflow ฉบับร่างแล้วอ่านกลับได้
5. แก้ node/connection แล้วบันทึกและอ่านกลับได้โดยไม่สูญเสียข้อมูลที่รองรับ
6. เปิด/หยุดและทดลองรันได้เฉพาะเมื่อ API รองรับและมีการยืนยันตามที่กำหนด
7. execution history ตรงกับข้อมูลจริง
8. ภาษา UI เป็นภาษาไทยและใช้งานได้บนหน้าจอมือถือ
9. ทดสอบ validation, malformed JSON, unknown workflow ID, API failure, repeated click และ XSS payload
10. รันชุดทดสอบที่เกี่ยวข้องและเก็บผลลัพธ์จริงก่อนรายงานความสำเร็จ

ถ้าไม่มี Workflow จริงหรือไม่มี credentials พร้อม ให้ทดสอบด้วย workflow ทดสอบที่ปลอดภัยและไม่ส่งข้อมูลออก โดยไม่แตะต้องงานจริงของผู้ใช้

## 9. แผนแบ่งระยะ

- ระยะ 1: สำรวจ API/schema และความสามารถจริง, เพิ่มการทดสอบ gateway
- ระยะ 2: หน้าศูนย์ควบคุมภาษาไทยและรายการ/ประวัติ
- ระยะ 3: สร้าง Workflow จากภาษาไทยผ่านแม่แบบ/แผนที่ตรวจสอบได้
- ระยะ 4: Visual Editor และ round-trip test
- ระยะ 5: ปุ่มควบคุมจริง, hardening, regression tests และตรวจหลัง deploy

แต่ละระยะต้องผ่านการทดสอบก่อนดำเนินต่อ และต้องหยุดอย่างปลอดภัยเมื่อ API/สิทธิ์ไม่เพียงพอ

## 10. การรักษาสภาพเดิม

- ห้ามใช้ `git reset --hard`, `git checkout --`, `git clean` หรือคำสั่งที่ทิ้งงาน
- ก่อนแก้ไขให้บันทึก `git status`, สำรองเฉพาะไฟล์ที่จะเปลี่ยน และตรวจ diff
- ไม่แตะไฟล์ที่แก้ไขอยู่แล้ว เว้นแต่จำเป็นต่อขอบเขตงานและตรวจความต่างก่อน
- ไม่ commit จนกว่าจะได้รับอนุญาตอย่างชัดเจน
- เอกสารนี้เป็นแบบออกแบบเท่านั้น ยังไม่ได้เปลี่ยนโค้ดหรือสั่งงาน Workflow จริง

## 11. ประเด็นที่ต้องยืนยันจากสภาพแวดล้อมก่อนลงมือ

- n8n API version และ endpoint/schema ที่ API key มีสิทธิ์ใช้
- มีชุด node/แม่แบบใดพร้อมใช้และมี credentials ใดตั้งค่าไว้แล้ว โดยตรวจสถานะโดยไม่เปิดเผยค่าลับ
- วิธีเข้าถึงหน้า UI ผ่าน tunnel/proxy ปัจจุบัน
- หากต้องการแปลงภาษาธรรมชาติด้วย LLM จะใช้ provider ที่ตั้งค่าไว้แล้วหรือใช้แม่แบบเป็นค่าเริ่มต้น

การตรวจสอบเหล่านี้เป็นงานสำรวจ/ทดสอบในแผน implementation ไม่ใช่ข้ออ้างว่าความสามารถดังกล่าวพร้อมแล้ว
